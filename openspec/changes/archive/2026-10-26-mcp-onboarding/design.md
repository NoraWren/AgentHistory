# 设计：MCP 接入面板

## 背景

动机见 `proposal.md`。这里只记录影响实现的现状。

本机六个客户端的接入方式各不相同，实测到的位置与格式：

| 客户端 | 登记位置 | 格式 | 官方命令 |
| --- | --- | --- | --- |
| Codex | `~/.codex/config.toml` | TOML，`[mcp_servers.<名>]` 段 | 无 |
| WorkBuddy | `~/.workbuddy/connectors/default/mcp.json` | JSON，`mcpServers.<名>` | 无 |
| Kimi Code | `~/.kimi-code/mcp.json` | JSON，`mcpServers.<名>` | 无 |
| Claude Code | `~/.claude.json` | JSON，顶层 `mcpServers` 加按项目嵌套的 `projects.<路径>.mcpServers` | `claude mcp add/remove/list` |
| OpenCode | `~/.config/opencode/opencode.json` | JSON | `opencode mcp add` |
| DeepSeek Harness | 插件目录加 profile 登记 | 插件包 | 安装插件 |

几个必须绕开的具体情况：

- Claude Code 的 `~/.claude.json` 本机有 9 个项目层级，每个都有自己的 `mcpServers`。写到错的层级完全不生效，而且不会报错。
- OpenCode 的 `opencode.json` 旁边存在 `opencode.json.ocx-conflict-bak`，说明有别的工具也在改这个文件，直接写入会被覆盖。
- WorkBuddy 的 `mcp.json` 里已有近百条其他服务登记，其中多数带 `"disabled": true`。只增删自己那一条是硬性要求。
- `halo/CLAUDE.md` 是指向 `AGENTS.md` 的软链。目前不涉及，但说明这类目录里存在软链，做任何文件写入都要先判断是不是链接。

## 目标与非目标

**目标：**

- 六种客户端用同一套模型描述：位置、格式、写入方式（CLI / 文件 / 插件）。
- 握手检查可以脱离界面单独调用，便于测试与脚本。
- 写入路径全部可回退。

**非目标：**

- 不做远程或多机同步。
- 不管理其他 MCP 服务的配置，本服务之外的登记一律不动。
- 不负责启动或重启客户端，只如实说明需要重启。
- 不在本次引入记忆条目或改动 `history.db` 结构。

## 决策

**用注册表描述客户端，而不是为每个客户端写一段分支。** 每个客户端一条记录：根目录、登记文件、格式类型、是否支持官方命令、接入方式分类。新增客户端只需加一条。替代方案是逐客户端写 `switch`，接入两个新客户端的成本会线性上升，且容易漏改。

**判定以握手为准，配置文件只用于定位和写入。** 三步分开：先在文件里找登记，再确认登记指向的可执行文件存在，最后拉起子进程走 `initialize` 与 `tools/list`。任一步失败都落到不同的失败原因，这样界面能说清是「没配置」「路径失效」还是「进程起不来」。只看文件会把本机现在这种「配置在但连不上」误报成已接入。

**握手实现为同步子进程加超时，不引入常驻进程。** 复用 `AgentHistory mcp` 自身，不需要另起服务；超时上限设为 5 秒，超时按失败处理并释放进程。替代方案是复用客户端连接，但拿不到客户端的连接状态。

**有官方命令就走官方命令。** `claude mcp add`、`opencode mcp add` 知道该写哪一层、什么 schema，还能避免和别的工具抢同一份文件。代价是命令失败时要如实报错，不能退回文件写入——静默改文件正是这类问题的来源。

**文件写入采用「读全量 → 只改自己那条 → 写回」并先备份。** JSON 用 `JSONSerialization` 保结构，TOML 用行级定位定位到 `[mcp_servers.<名>]` 段再整体替换该段，段外面的内容逐字节保留。替代方案是用 TOML 库重写整个文件，会重排格式、丢注释，用户不会接受对一个手写配置文件做这种改动。

**插件式接入单独建模。** DeepSeek Harness 的可用性取决于插件是否安装，和「配置里有没有一条」不是同一件事。用独立状态表示，界面不提供「接入」按钮，改为给安装指引。

**状态展示放在面板与菜单栏，不做启动弹窗。** 未接入是常态，不是错误；只有已接入的客户端握手失败才提示一次。

## 风险与取舍

- [官方命令的参数随版本变化] → 调用前用 `--help` 确认子命令存在，不存在则回退到文件写入并在结果里说明走了哪条路。
- [生成新配置时把 TOML 段插错位置] → 只追加到文件末尾的 `[features]` 之类顶层段之前；解析失败则不写并报错。
- [TOML 行级替换误伤相邻段] → 替换范围限定在目标段标题到下一个段标题之间，写前备份，写完重新解析校验段数不变。
- [与 opencodex 等工具并发写同一文件] → 写前记录文件修改时间与大小，写后核对未被外部改动，改动则回滚并提示重试。
- [握手拉起子进程触发一次补同步] → 握手不执行任何工具调用，只走 `initialize` 与 `tools/list`，不触碰同步逻辑。
- [界面在检查期间卡顿] → 检查在后台执行，界面先显示上次结果并标注检查中。

## 迁移方案

不涉及数据结构迁移。首次打开面板即完成一次全量检查，无需用户做任何准备。移除路径为删除新增模块与面板入口，已写入的客户端配置可用面板的移除动作清理，不依赖新代码。
