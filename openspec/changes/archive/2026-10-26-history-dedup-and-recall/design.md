# 设计

## 背景

动机见 proposal.md。这里只记录决定实现形状的现状约束，数字均取自本机统一库（2,302 个会话、211,590 条记录、337MB）。

| 现象 | 实测值 | 对设计的影响 |
| --- | --- | --- |
| handoff 记录 | 1,527 条已转出记录，覆盖 770 个来源会话 | 已有现成的副本证据，不必从零推断 |
| 同名跨源会话 | Kimi 653/758、WorkBuddy 728/746 与 Codex 同名 | 标题是强信号，但单独用会误伤 |
| 标题重复但内容不同 | 「你好」「hi」「Request URL」等同名族最多跨 25,031,249,683 毫秒（约 290 天） | 必须有内容签名把关 |
| 正文完全重复的组长文本 | 11,066 组 | 同一内容摘要做一级判据可行 |
| 检索名额浪费 | 搜「易得广场」60 条命中只覆盖 35 个会话 | 条目级检索必须改成会话级 |
| 工具输出占比 | items 里 49,517 条 commandExecution、10,140 条 fileChange | 检索默认要能排除工具日志 |
| 超大会话 | 单会话 5,443 条 | 跳转必须直取，不能翻页 |
| 脱敏 | 入库即遮蔽，`raw_json` 全部丢弃 | 导出只能输出遮蔽后的文本 |

## 目标与非目标

**目标**

- 默认视角下，一个内容族只出现一次，列表和检索都按族计数。
- 检索结果按会话聚合，带筛选，跳转能落到任意条目。
- 单会话、项目、检索结果三种范围都能导出成可归档的 Markdown。

**非目标**

- 不删除库内的副本。副本仍然是数据，只是默认不占展示位；关闭去重即可看到全部。
- 不做跨设备同步，不引入服务端。
- 不还原被遮蔽的原文，导出也不提供原文选项。
- 不改动各客户端的原始历史。

## 决策

### 血缘以同步记录为主，内容签名为辅

副本判断分三级，优先级从高到低：

```
  handoffs 里的转出记录 ----(直接指定)----> 关系确定，标记 confirmed
           |
           v  没有转出记录时
  标题 + 项目路径 + 内容签名 ----(全部一致)--> 关系推断，标记 inferred
           |
           v  任一不一致
       视为独立会话，不建关系
```

内容签名定义为 `条目数 + 正文总字符数`。选它而不是正文哈希，原因是同步过程会在目标端注入元数据行，逐字哈希几乎必然不相等；而「条目数 + 总字数」在实测中能把 294 组同内容不同来源的会话稳定对齐，同时把「你好」这类同名不同内容的会话挡在外面。

只按标题归族是错的，这一点有数据支撑：本机 569 个同名族里，时间差最大的一条跨越约 290 天，是不同时期的两次「你好」。这类会话一旦被合并，用户就会以为自己的历史丢了。

### 关系表与家族表分开

两张新表：

```
thread_families   id, representative_thread_id, member_count, created_at
thread_links      family_id, thread_id, role(original|copy), relation(confirmed|inferred),
                  direction, target_ref, created_at
```

代表会话存进 `thread_families` 而不是每次查询时现算。现算需要每次 JOIN 全部会话并排序，2,302 个会话时还能忍，增长到万级就会拖慢列表。固定下来还有一个好处：代表是哪条会话，重启、重同步之后都不变，符合规格里「代表会话稳定」这条。

代表会话的选取规则写死在重建逻辑里：先按 `created_at` 升序，再按 `SourceKind` 声明顺序升序。这样同族里 Codex 原创优先于 Kimi 副本，符合直觉。

### 检索聚合在 SQL 层做，不在内存里做

改成两段查询：

1. 先用 FTS5 取命中的条目行，带 `bm25` 分。
2. 再按内容族分组，每族取分最高的那一条作为代表，其余折叠成命中计数。

分组用一次 JOIN 而不是把命中拉进内存：FTS5 的 `match` 结果是按相关性排好的，在 SQL 里用窗口函数按 `family_id` 分区取 `row_number()=1` 就能拿到每族最佳，System SQLite 3.54 支持窗口函数。

配套两条索引：`thread_links(thread_id)` 用来从会话查族，`thread_families(representative_thread_id)` 用来从族查代表。

### 排序规则向短语命中倾斜

现有查询把连续汉字拆成单字后用 AND 连接，问题是不区分「表格」连写与「表」「格」分处两句。做法是给每个查询词生成两个 `match` 表达式：短语版 `"表 格"` 和单字版 `"表" AND "格"`，先跑短语版，短语版结果不足限额时再用单字版补齐，并在结果上标记来源是短语命中还是宽松命中。

排序键改为：短语命中优先，其次 `bm25`，最后按会话最近活动时间倒序。这样不需要改切词逻辑，也不用重建索引，只改查询。

### 跳转按序号直取

现在的 `openHit` 靠反复 `loadMore` 往前翻，最多翻 20 页共 4,000 条，单会话 5,443 条时后面 1,443 条永远跳不到。改成先用命中条目的 `ordinal` 查一次「该会话里 `ordinal` 小于目标的记录数」，算出它落在第几页，直接用 `OFFSET` 定位，再按 200 条一页往下取。

代价是一次带 `OFFSET` 的查询；有 `idx_items_thread(thread_id, ordinal)` 在，实测这种量级是毫秒级。

### 导出走同一套格式化，界面与命令行共用

`Sources/Core/Export.swift` 里放纯函数：会话元数据加条目列表进，Markdown 字符串出。界面按钮和 `export` 子命令都调它，避免两边格式漂移。

导出文件的结构固定：

```
# 标题
> 来源 / 项目 / 时间范围 / 记录数 / 遮蔽条数
（正文：按轮次分节，工具输出折叠成引用块）
```

工具输出在导出里降级成引用块并截断到固定长度，正文完整性优先给用户消息和助手回复。这条与现有的索引取舍一致：工具输出占正文体积的大头，全量导出会让文件失去可读性。

批量导出的清单写成 `index.md`，列出文件名、标题、来源与遮蔽条数。同名冲突按规格改序号而不覆盖。

### 去重开关默认打开，状态持久化

默认合并是这次变更的核心价值，所以默认打开；但「看到全部」是排障和核对同步结果的必要能力，所以开关必须存在并记住上次选择。状态存 `UserDefaults`，与现有的来源筛选、项目筛选同样处理。

## 风险与取舍

- 内容签名碰撞，把两次不同对话合并成一条 → 签名要求标题、项目路径、条目数、总字数四项同时相等，且推断关系在界面上标注来源为「按内容推断」，用户能自行判断。
- 血缘重建在 2,302 个会话上耗时不可控 → 重建时按签名分组做一次批处理，预期在数秒内；若超过 10 秒改成后台任务并显示进度。
- 聚合后用户以为会话少了 → 列表与状态栏都显示合并前后两个数字，例如「798 个会话（合并前 2,302）」。
- 窗口函数在旧系统 SQLite 上不可用 → 目标系统是 macOS 14，系统 SQLite 3.54，已确认支持；实现时加一条降级路径：不支持时退回内存分组。
- 导出把脱敏占位符带进文档，影响粘贴出去的观感 → 文件头写明遮蔽条数，占位符保持原样，让读者知道原文被有意遮蔽。
- 批量导出大项目时文件数过多 → 清单 `index.md` 作为唯一入口，文件名用会话标题加短标识，避免 500 个 UUID 命名的文件。

## 迁移计划

1. 启动时按 `schema_version` 迁移，新增两张表与两条索引，不动既有表结构。
2. 首次迁移后跑一次血缘重建，从 `handoffs` 反推已转出的副本关系，再对剩余会话做内容签名比对。
3. 迁移期间列表照常可用，去重开关在血缘为空时等于没有效果，不会报错。
4. 回滚方式是删除两张新表并清空版本号，既有会话、条目、检索索引不受影响。
