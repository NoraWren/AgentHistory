# 设计

## 背景

本机四个客户端的存储结构都在 2026-10-23 实测过：

| 来源 | 权威存储 | 实测规模 |
| --- | --- | --- |
| Codex | `~/.codex/thread_history_1.sqlite` 与 `state_5.sqlite` | 816MB / 5.1MB，758 会话，156,984 条目 |
| Claude Code | `~/.claude/projects/*/*.jsonl` | 29 个文件，4.7MB |
| WorkBuddy | `~/.workbuddy/projects/*/*.jsonl` 与 `workbuddy.db` | 4 个文件，6.0MB，4 个会话 |
| OpenCode | `~/.local/share/opencode/opencode.db` | 6.1MB，15 会话，3,308 条消息 |

三个约束决定了方案形状。Codex 的 758 个会话里，633 个的 rollout 原件已不存在，正文只剩投影库；四份存储里三份是 WAL 模式、客户端运行时仍在写；正文中有 219 条形似凭据的字符串。

## 目标与非目标

**目标**

- 首次全量同步在一分钟内完成，日常增量在数秒内完成。
- 界面显示即可用，不依赖浏览器、端口或后台服务。
- 同一个可执行文件同时承担图形界面、命令行同步和 MCP 服务。

**非目标**

- 不做多设备同步，不引入服务端。
- 不改写来源客户端的数据库。
- 不保证把任意会话无损导入所有客户端。

## 决策

### 单一可执行文件，三个入口

应用包内的同一个二进制按参数分派：无参数启动界面，`mcp` 进入 stdio MCP，`sync` 执行命令行同步。界面与 MCP 共用同一套查询函数，读同一个 `~/.agent-history/history.db`。

备选是“界面进程加本地 HTTP 服务”，但那样要管端口、进程生命周期和权限，还会让界面与 agent 看到两份可能不同步的状态。单进程没有这些问题。

### 统一库的表结构

```
sources       来源定义、适配器版本、上次同步时间
projects      归一化项目，主键是真实路径
threads       会话，唯一键为来源加来源内标识
turns         轮次，保留开始、结束与状态
items         条目，按轮次序号排序，正文与结构化摘要分开
search_docs   FTS5 索引，存放切词后的检索文本
handoffs      交接包
sync_state    每个来源、每个会话的水位
```

`items` 存原始文本，`search_docs` 只存切好词的检索形态，两者用条目主键关联。正文与检索形态分开，是因为中文切词会插入空格，直接显示会变成“止 损 线”。

### 增量水位按来源分别设计

- Codex：`thread_items` 上有现成的 `(thread_id, updated_at_ordinal)` 索引，按会话记录 `max(updated_at_ordinal)`，每次只取大于水位的行。`threads` 表用 `updated_at` 做第二层水位，先筛出有变化的会话。
- JSONL 来源：记录 `inode + 文件大小 + 已读字节偏移`。追加写只读尾部；文件变小或 inode 变化时整文件重读。
- OpenCode：按 `message.time_updated` 与 `part.time_updated` 拉增量。

最近一天有 3,333 条新条目、7 天 23,317 条，日常增量规模很小。

### 中文检索自己切词

系统 SQLite 3.54 带 FTS5，但默认 `unicode61` 分词器不切中文，实测搜索「止损线」返回 0 条；`trigram` 分词器要求三字以上，「止损」仍为 0。

方案是入库前把连续汉字拆成单字、英文与数字保留整词，查询时同样处理并用短语 AND 连接。实测「止损线」「止损」「跨境电商」「3000」都能命中。切词只在写入和查询两处发生，界面显示的一直是原始文本。

实测代价：96,177 条对话文本切词建索引，落盘 97.4MB，耗时 6.7 秒，查询在毫秒级。

### 正文只收对话，工具输出降级保存

Codex 的 610MB 条目正文里，命令执行和工具调用占 493MB，会让检索结果被参数和日志淹没。索引只收用户消息、助手回复、推理摘要和计划；工具调用只保留命令与截断后的输出摘要，保留跳转所需的位置信息。

### 敏感信息在入库时遮蔽

按形态匹配 API Key、GitHub 令牌、GitLab 令牌、JWT、Bearer 令牌和私钥块，保留首尾少量字符。认证文件和连接器令牌文件不读取内容。

### 目标写入按能力分级

实测结论直接决定产品行为：

| 目标 | 方式 | 验证状态 |
| --- | --- | --- |
| OpenCode | 生成标准导出 JSON，调用 `opencode import` | 已跑通：外部会话导入后 1 会话 / 2 消息 / 2 片段，导出可读 |
| Codex | 生成交接包，用 `codex exec` 或 `codex exec resume` 注入 | 手工伪造 rollout 经 `migrate-rollouts` 只留下会话条目，正文丢失，因此不走伪造 |
| Claude Code | 生成会话 JSONL 写入对应项目目录 | 格式已取样，恢复入口未验证，先标为实验性 |
| WorkBuddy | 生成会话 JSONL 并登记会话表 | 无官方导入入口，需关闭应用后写入，风险最高 |

WorkBuddy 这一行在核实后可以更准确：它的服务端用 `collectConversationFiles` 扫描 `configDir/projects/*/*.jsonl`，文件名去掉后缀就是会话标识，旁边可选一个 `.meta.json`。所以写入会话文件即可被发现，数据库登记是次要的，仍需启动后实测确认。

预览阶段就把“原生导入”还是“交接包”写清楚，用户不会在执行完才发现只是复制了一段文字。

### 预览是真实的试运行

点“同步”前先跑一遍不写盘的完整流程，产出一份计划对象：会话数、消息数、目标路径、重复项、遮蔽条数、预计字节数。计划对象存在内存并向界面输出，用户确认后执行阶段严格按计划落盘。这样预览数字和实际写入不会是两套逻辑。

### 进度按阶段加权

读取 0–25%，归一化 25–45%，遮蔽 45–60%，写入 60–90%，校验 90–100%。每个阶段都有已完成量和总量，界面显示当前阶段名。总量来自预览计划，不是估算。

### 界面用 SwiftUI，绕开宏

本机只有 Command Line Tools，没有 Xcode，`@State` 这类宏插件缺失会直接编译失败。界面统一用 `ObservableObject` 加 `Binding`，`swiftc` 直接出可执行文件再组装应用包。已在 macOS 27 上实测编译、启动并读取真实会话列表。

部署目标设为 macOS 14.0，编译期即可拦截高于该版本的 API。

### 备份与回滚

写入目标前，把目标文件复制到 `~/.agent-history/backups/<时间戳>/`，SQLite 目标用 `VACUUM INTO` 生成快照。失败或校验不通过时按快照恢复，并保留失败原因。

### 客户端全部可选

适配器在启动时探测目录是否存在，缺失的客户端不注册来源、不出现在界面，也不计入进度总量。同步计划只包含实际存在的来源与目标。本机同时只有 Codex 和 WorkBuddy 时，工具只跑这两个适配器。

### 用 MCP 直读补住不支持导入的客户端

目标客户端没有可写入口时，比交接包更稳的办法是让它在会话里直接查历史：把本地 MCP 服务注册进目标客户端，agent 通过 `search_threads` 与 `get_thread_context` 读取统一库。这样数据只留在统一库，不需要碰目标客户端的私有格式。

Codex 与 WorkBuddy 都支持 stdio MCP：Codex 用 `codex mcp add`，WorkBuddy 的 `~/.workbuddy/connectors/default/mcp.json` 里有 10 个 stdio 形态的连接器，可以照同样结构追加。

## 风险与取舍

- 来源库名带版本号（`state_5.sqlite`），客户端升级后会改名。→ 适配器启动时扫描同名前缀的最新编号文件，并在状态页显示实际使用的文件。
- 客户端运行中写入可能产生锁。→ 只读打开并设置忙等待，失败重试三次，仍失败则跳过该会话并记录。
- 写入其他客户端属于非官方路径，可能被对方升级破坏。→ 写入前强制备份，预览中标注实验性，失败时不影响统一库。
- 会话正文含有大量工具输出，索引膨胀。→ 工具输出只保留摘要，必要时按需回源读取。
- 中文切词会让索引体积翻倍。→ 实测 97MB，可接受；若继续增长再按项目分片。

## 迁移计划

首次启动创建统一库并做全量同步，界面显示进度。若中途退出，下次从水位继续，不会重复写入。升级适配器版本时只重建受影响的来源分区，不影响其他来源。

## 待确认

- Claude Code 写入会话文件后能否在其恢复列表中出现，需要在实现阶段用隔离配置目录验证；验证失败则降级为交接包。
- WorkBuddy 的正确写入时机（应用关闭后）需要在实现阶段确认。

## 实测记录

2026-10-23 在实现阶段测得：

- 首次全量同步：772 个会话、110,161 条记录，36.6 秒。
- 二次增量同步：0.2 秒；Codex 按 `updated_at_ordinal` 只取新增行。
- 统一库体积：约 185MB（已去掉逐条原始 JSON，正文与检索分词各存一份）。
- 中文检索：「止损线」命中 52 条原始记录，两字「止损」同样命中。
- 脱敏复核：落库文本中六类密钥形态的精确匹配计数均为 0。
- OpenCode 导入：1 个会话、345 条消息、345 个片段，导入后可导出原文。
- WorkBuddy 写入：沙盒目录中生成会话 JSONL 与 `.meta.json`，格式与其自身文件一致。
